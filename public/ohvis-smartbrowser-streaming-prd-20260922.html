1. 배경 및 문제 정의

현재 오비스 스마트브라우저는 서버 레인(Playwright 헤드리스)과 PC 레인(PC Agent 경유) 두 실행 경로를 갖고 있으나, 화면은 3초 폴링 스크린샷(읽기전용)만 제공한다. AI가 화면을 분석해 클릭·입력을 결정하는 과정에서 오탐지·지연이 발생해도, 대표님이 그 시점에 직접 개입할 방법이 없다 — 개입하려면 별도 채널(PC 원격 접속)을 거쳐야 한다.

대표님 요청 요지: "AI가 느리고 틀리는 경우, 내가 화면을 보면서 직접 빠르게 클릭·입력하고, 그 조작을 레시피로 남겨 다음부터는 AI가 그대로 재사용하게 해달라."

2. 목표 / 비목표

목표

  • 서버 레인·PC 레인 브라우저 화면을 채팅창 내에서 실시간(지연 최소화)으로 확인한다.
  • 대표님이 스트리밍 프레임 위에서 직접 클릭·타이핑해 진행 중인 작업에 개입할 수 있다.
  • 대표님이 수행한 조작을 자동으로 단계 기록하고, 승인 시 work_recipes 로 등록해 다음 실행부터 AI가 재사용한다.

비목표 (이번 범위 제외)

  • 서버 레인 화면을 영상 파일로 저장·재생하는 기능 (증거 스크린샷으로 충분)
  • 복수 대표님 동시 접속·공동 조작 (1세션 1조작자 가정)
  • 모바일 앱에서의 프레임 조작 (데스크톱 대시보드 우선, 모바일은 조회만)

3. 사용자 시나리오

시나리오 A — 정상 자동 진행 중 개입 없음

대표님이 레시피 실행을 승인 → 서버 레인 브라우저가 자동 진행 → 채팅창에 실시간 프레임이 흐르지만 대표님은 지켜보기만 함 → 완료 시 증거와 함께 완료 보고.

시나리오 B — 봇차단·오탐지로 AI가 막혔을 때 대표님 개입

서버 레인이 server_ip_blocked 또는 반복 클릭 실패로 정체 → 채팅창 스트림 프레임 위에 "개입 필요" 배지 표시 → 대표님이 프레임을 직접 클릭·입력 → 성공 시 해당 스텝이 자동으로 record_step 대기열에 쌓임 → 대표님 승인 시 work_recipes v+1 로 등록 → 다음 실행부터 AI가 그 스텝을 재사용.

시나리오 C — PC 레인 필요 사이트(공동인증서 등)

native_auth_required 판정으로 PC 레인 전환 → PC Agent의 Chrome CDP 화면이 채팅창에 스트리밍 → 대표님이 PC에 설치된 인증서로 직접 인증 → 이후 스텝은 다시 AI가 자동 진행.

FR1 서버 레인 CDP screencast 프레임을 WebSocket으로 채팅창 패널에 스트리밍 서버 구현 CDP Page.startScreencast 프레임을 WS로 전송하는 경로 구현·검증(실브라우저 CDP 테스트 통과). 프론트 렌더 연동은 별도 확인 필요.
FR2 대표님이 프레임 위에서 클릭·타이핑한 좌표/텍스트를 CDP Input 이벤트로 원본 브라우저에 되돌림 서버 구현 클릭·텍스트·Enter를 동일 CDP 세션의 Input.dispatchMouseEvent/Input.dispatchKeyEvent 로 전달하는 경로 구현·검증.
FR3 대표님의 성공한 조작을 record_step 으로 자동 기록 → 승인 시 work_recipes v+1 생성 API 존재 + 연동 조작 기록→승인→레시피 생성 API는 기존에 존재(오비스 E2E 레시피 등록 574ba7d0 로 검증됨). 이번 스트리밍 조작을 그 큐로 넘기는 연결부 구현.
FR4 PC 레인(PC Agent) 화면도 동일한 방식으로 스트리밍·조작 가능 조사 중 PC Agent 양방향 WebSocket과 chrome_cdp/interactive_browser capability는 선언돼 있으나(pc_agent_manager.py:216), 실제 screencast 업링크 연결 여부는 이번 턴 종료 후 실측 예정.
FR5 레시피 승인/반려 대시보드 화면 (대표님이 API 없이 화면에서 처리) 구현·배포됨 runner-4e41ef97 로 구현, 재검수 통과 후 배포 완료(backend=OK).

5. 비기능 요구사항

항목요구 기준
지연시간프레임 표시 지연은 체감 개입이 가능한 수준(수백 ms대)을 목표로 한다. 기존 3초 폴링 대비 현저히 개선되어야 한다. 실측 수치는 [미측정] — 배포 후 측정 필요.
보안조작 스트림은 승인된 세션에서만 열리며, 시크릿 입력 필드(비밀번호 등)는 레시피 기록 시 마스킹한다. 금융·인증서 화면은 PC 레인으로만 개입(R-KEY, R-AUTH 준수).
감사모든 수동 개입 스텝은 조작자(대표님) 식별과 함께 기록되어 handover/DB에 남는다.
무중단스트리밍 세션이 열려 있는 동안 Blue-Green 배포는 target_drain_busy 로 자동 대기하며, 강제 종료하지 않는다(2026-09-22 00:31 KST 실측: 배포 #5022가 이 사유로 자동 취소·후속 배포로 대체됨 — 정상 동작).

8. Acceptance Criteria (완료 판정 기준)

  • 서버 레인 실행 중 채팅창에서 실시간 프레임이 3초 폴링보다 명확히 빠르게 갱신되는 것을 화면 캡처로 확인
  • 대표님이 프레임 위 클릭 시 원본 브라우저에서 해당 좌표 클릭이 재현되는 것을 스크린샷 전/후로 확인
  • 수동 조작 1건 이상이 record_step → 승인 화면 → work_recipes 로 이어지는 것을 DB row로 확인
  • PC 레인에서도 동일 스트리밍·조작이 최소 1개 사이트에서 재현
  • Blue-Green 배포 후 candidate/green 동일 digest + health 200 + 5분 무오류 감시
