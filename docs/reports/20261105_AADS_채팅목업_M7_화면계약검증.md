## 결론과 한계

실제 /chat Next 라우트(dev 서버)에서 시나리오 4a–4g 를 데스크톱 1440×1000 과 모바일 390×844 로 실행했고 모두 통과했다. 결과 표기는 **실제 /chat 화면·계약 모의 검증**이다. **실제 백엔드 실연동은 M9 로 이관, 미검증**이다(서버 응답은 aads-server mockup-review 라우트·메서드·경로·본문을 그대로 따르는 모의 API 가 만들었다). "실연동 성공"이 아니다.

## 검증 방식

- 하니스 페이지 없음. 부팅 요청(auth, session, messages 조회)에는 서버 스키마에 맞는 픽스처로 답했다.
- Playwright 네트워크 가드: context 의 route('**/*') 가 dev 출처와 모의 API 출처만 통과시키고 나머지는 전송 전에 중단·집계한다. service_workers='block'. 예상 밖 non-GET 은 즉시 실패. WebSocket 은 dev HMR 만 통과.
- 엄격 모의 API(tests/browser/mockup-chat/strict_mock.py): 승인 본문(revision_id, 64자리 소문자 16진 manifest_hash — 실제 sha256, expected_generation, confirm=true, idempotency_key), 수정 요청 접수 본문, 멱등 재생·충돌, 모든 쓰기의 generation 증가, expected_generation 불일치 409, 판본별로 내용이 다른 문서와 revision 쿼리 값 검증.
- 기존 sandbox/CSP 보존 확인: html_preview iframe 안의 스크립트는 브라우저가 실제로 차단했다(4a).

## 발견한 제품 결함과 처리

1. 모바일 카드의 "우측 패널에서 보기 →" 가 시트를 열지 않았다. page.tsx handleViewArtifactStable 에서 모바일이면 setMobileOverlay("artifact") 를 호출하도록 수정. 회귀: mockupCardMobileOpen.test.ts, 4a 모바일.
2. 모바일에서 패널로 장전하면 패널이 닫혀 후보 목록만 남고, 후보가 여럿이라는 이유만으로 전송이 조용히 막혔다. mockupTargetStore.ts sendResolution 에서 "reply_vs_panel" 불일치만 막고, 직접 장전한 대상은 그대로 보내도록 수정. 회귀: mockupTargetStore.test.ts, 4c 모바일.
3. 세션을 빠르게 전환하면 늦게 도착한 이전 세션의 아티팩트 응답이 새 세션 목록을 덮어썼다(4e 에서 재현: B 화면에 A 의 패널·아티팩트가 남아 수정 요청이 막힘). page.tsx 세션 전환 effect 의 아티팩트 조회 결과를 effect 정리 뒤에는 버리도록(`if (cancelled) return;`) 수정. 회귀: mockupCardMobileOpen.test.ts, 4e.
4. (미수정, 보고만) 연속으로 두 번 보내면 응답 말풍선의 render_id 가 ai-streaming-<세션> 으로 재사용되어 React 중복 key 경고가 나고 Next dev 오버레이가 심볼 복원 POST 를 낸다. 기존에 알려진 특성(chatViewportController 주석, 운영 S9 2026-10-13)이며 목업과 무관해 제품 코드는 건드리지 않았다. 테스트는 이 경고와 dev 도구 POST 만 허용하고 그 밖의 콘솔 오류는 실패로 처리한다.

## 지시서와 다른 점

- 지시서의 change-intake 본문에 base_revision_id 가 있었으나 서버 ChangeIntake 모델에는 없다. 서버를 따라 보내지 않고(클라이언트도 보내지 않음), 기준 판은 서버가 최신 판으로 정한다. 모의는 이 필드가 오면 계약 위반으로 기록한다.
- 저장 실패 뒤 입력창 보존: 앱은 같은 멱등 키로 자동 재시도하고(말풍선 유지), 소진되면 입력창에 같은 내용을 되돌려 놓고 안내를 띄운다. 저장 안 된 말풍선에는 "입력창에 복사" 버튼이 없고 "회수"만 있다.
